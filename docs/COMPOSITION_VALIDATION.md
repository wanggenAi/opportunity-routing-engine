# Composition Validation Ledger

Status: `CANONICAL POST-CALLABILITY VALIDATION / FAIL-CLOSED`

## Purpose

A `CALLABLE_COMPOSED` resource composition proves only that every required capability has fresh confirmed evidence, confirmed/committed availability and allowed permission.

It does **not** prove that the operator can execute the route, that counterparties consent, that the payer is clear or committed, that economics work, or that legal/trust/safety conditions pass.

This layer persists those downstream validation facts against one exact immutable composition hypothesis:

```text
composition_run_id
+
hypothesis_index
```

Validation history is append-only. Later evidence changes the time-scoped projection; it does not erase earlier evidence.

## Canonical hard gates

This module does not redefine G0-G6. It preserves the existing canonical meanings:

```text
G0 Actor / role clarity
G1 Payer clarity
G2 Transactionability
G3 Legal / trust / safety
G4 Capability decomposability / delegatability
G5 Orchestration value
G6 Regenerative circulation / recurring demand
```

Only G0-G3 are projected here. G4-G6 remain outside this ledger because one bounded transaction-validation record cannot manufacture strategic sustainability truth.

## Independent validation dimensions

```text

OPERATOR_ACCESS
COUNTERPARTY_VISIBLE_SURPLUS
COUNTERPARTY_CONSENT
PAYER_COMMITMENT
ECONOMICS
LEGAL_TRUST_SAFETY
```

Each dimension remains independent.

Hard boundaries:

```text
PAYER_CLARITY != PAYER_COMMITMENT
OPERATOR_ACCESS != COUNTERPARTY_CONSENT
COUNTERPARTY_VISIBLE_SURPLUS != PAYER_COMMITMENT
PAYER_COMMITMENT != ECONOMICS
CALLABLE_COMPOSED != TRANSACTIONABILITY
ONE VALIDATION DIMENSION != ANOTHER
UNKNOWN != PASS
```

## Access semantics are reused, not duplicated

`OPERATOR_ACCESS` is not a new PASS/FAIL classifier.

The only accepted access states are the existing canonical `AccessState` values from `src/access_feasibility.py`:

```text
UNASSESSED
ACCESS_BLOCKED
INTRODUCTION_READY
ENGAGEMENT_READY
VALIDATION_ACCESS_READY
```

Reviewed access intake carries a full `AccessFeasibility` record. The event value is generated by the existing `access_state(record)` function.

The intake rejects a hand-written access value so the validation layer cannot bypass access/backing/visible-surplus semantics.

## G0-G3 projection

### G0 — Actor / role clarity

Derived only from `ACTOR_ROLE_CLARITY`.

### G1 — Payer clarity

Derived only from `PAYER_CLARITY`.

Payer identity/role clarity is intentionally separate from actual payer commitment.

### G2 — Transactionability

G2 is fail-closed and requires all of the following:

```text
CALLABLE_COMPOSED
+
NEED_CONFIRMATION = PASS
+
OPERATOR_ACCESS = VALIDATION_ACCESS_READY
+
COUNTERPARTY_VISIBLE_SURPLUS = PASS
+
COUNTERPARTY_CONSENT = PASS
+
PAYER_COMMITMENT = PASS
+
ECONOMICS = PASS
```

If canonical access is `ACCESS_BLOCKED`, G2 is `FAIL`. Intermediate access states remain `UNKNOWN`, not PASS.

### G3 — Legal / trust / safety

Derived only from `LEGAL_TRUST_SAFETY`.

This is the only validation dimension that may assert `CONDITIONAL`, matching the existing opportunity-ranker contract.

## Reviewed intake

Use:

```bash
python scripts/import_composition_validations.py \
  --input validations.jsonl \
  --run-db state/composition-runs.db \
  --validation-db state/composition-validation.db \
  --as-of 2026-09-13T20:00:00+08:00
```

Generic events use an explicit allowlist and carry:

```text
validation_id
composition_run_id
hypothesis_index
dimension
value
observed_at
evidence_ref
evidence_note
subject_ref (optional)
details (optional)
```

`OPERATOR_ACCESS` uses `access_record` instead of `value`.

The intake explicitly rejects direct derived fields such as:

```text
transaction_ready
bounded_transaction_ready
G0
G1
G2
G3
G4
G5
G6
```

The summary produced by the CLI shows the time-scoped G0-G3 projection, but the projection is computed from stored evidence; it is not accepted from input.
