## 1. Operator role

The founder/operator is **not** the default field researcher, technology manager, consultant, salesperson, developer, QA person or delivery worker.

The founder/operator is the **Orchestrator / Principal / Routing Control Plane**.

Primary responsibilities:

```text
SEE STRUCTURE
→ DEFINE ACTOR ROLES
→ DEFINE EVIDENCE CONTRACTS
→ DESIGN HOOKS
→ OPTION ACCESS / CAPABILITY
→ DEFINE INPUT / OUTPUT / ACCEPTANCE
→ ALIGN INCENTIVES
→ ROUTE WORK
→ GOVERN TRUST / RISK
→ OBSERVE OUTCOME
→ REPLACE / COMPOSE RESOURCES
→ LEARN
```

The founder may temporarily perform one of the routable roles only when that is the cheapest honest way to learn an unknown boundary.

Founder execution is therefore a **calibration exception**, not the target operating model.

## 2. No role may silently collapse into the founder

The following are separate callable roles:

```text
ORCHESTRATOR / PRINCIPAL
ACCESS PROVIDER / INTRODUCER
FIELD SCOUT / NEED DISCOVERY
DOMAIN ANALYST
CAPABILITY PROVIDER / EXECUTOR
VALIDATOR / QA
CONTRACT / COMPLIANCE SUPPORT
PAYER / AUTHORITY
BENEFICIARY
RESOURCE OWNER
```

One person may temporarily hold several roles, but the system must record the roles separately.

The system must never infer:

```text
FIELD SCOUT = FOUNDER
TECHNOLOGY MANAGER = FOUNDER
DELIVERY PROVIDER = FOUNDER
QA = FOUNDER
```

simply because the founder is capable of doing the work.

## 3. Founder-dependence gate

A route is not scalable merely because the founder can make the first transaction work.

Every real route must record:

```text
founder_roles_performed:
founder_time_spent:
which_role_was_not_yet_optioned:
why_founder_execution_was_required:
what_evidence_would_allow_replacement:
next_external_actor_to_option:
```

A route may reach first-transaction proof while still founder-dependent.

But it may **not** be promoted to a reusable orchestration pattern until at least one material sensing/access/execution role has been demonstrated by a non-founder actor under explicit terms and evidence/acceptance rules.

The target is:

```text
FOUNDER KNOWS THE ROUTE
→ ROLE INTERFACES BECOME EXPLICIT
→ EXTERNAL ACTORS CAN PERFORM THEM
→ ACTORS BECOME REPLACEABLE / COMPOSABLE
→ FOUNDER RETAINS ROUTING / GOVERNANCE / CAPITAL-ALLOCATION ADVANTAGE
```

## 4. Field sensing itself is a routable capability

The project must treat reality sensing as part of the resource graph.

Possible sensor actors include:
- technology managers;
- implementation consultants;
- former enterprise software staff;
- accountants / tax-service people;
- industrial-park service personnel;
- equipment distributors / after-sales engineers;
- recruiters;
- logistics dispatchers;
- lawyers / compliance consultants;
- retired engineers;
- association staff;
- local channel operators;
- independent domain experts;
- customers and suppliers themselves;
- software / AI / public-data sensors.

The relevant unit is not the person's title. It is a callable sensing capability, for example:

```text
FIELD_SCOUT_CAPABILITY
scope: manufacturing digital-delivery problems
access_basis: existing customer / institutional / professional relationship
required_evidence:
  - recent event / task
  - actor and role
  - current workaround
  - cost / delay / people-days when knowable
  - payer / authority
  - external-collaboration boundary
  - original wording / source
forbidden:
  - invented demand
  - confidential customer data without permission
  - vague "they want AI" summaries
compensation:
  - explicit and voluntary
promotion:
  - accepted evidence packet / qualified opportunity / settled transaction, depending contract
```

This allows the founder to organize sensing without personally conducting every interview.

## 5. External archetypes — what already works in the real world

No single company is the exact target model. The closest structure is a **composite** of several proven orchestration mechanisms.

### A. Li & Fung — multi-node supply-chain orchestration

Observed mechanism:
- calls itself a supply-chain orchestrator;
- coordinates design/development, sourcing, compliance, manufacturing control and logistics;
- currently states that it works through a network of 4,800+ factories across 40+ production countries.

Why it matters:

```text
CUSTOMER OUTCOME
→ DECOMPOSE VALUE CHAIN
→ SELECT MULTIPLE SPECIALIZED RESOURCE NODES
→ GOVERN QUALITY / COMPLIANCE / TIMING
→ DELIVER ONE COHERENT RESULT
```

Lesson for this project:
- the orchestrator does not need to own every production asset;
- the durable asset is the ability to decompose, select, coordinate and govern a network;
- multi-party execution can still feel like one outcome to the buyer.

Do not copy:
- its domain concentration or operational overhead blindly.

Sources:
- https://www.lifung.com/
- https://www.lifung.com/suppliers/overview/

### B. Xometry — capability routing + machine-readable acceptance

Observed mechanism:
- buyers upload CAD/specification;
- software generates price / lead-time / manufacturability feedback;
- work is assigned to a vetted manufacturing partner network;
- partners may accept jobs matching their current capacity;
- Xometry states access to thousands of manufacturers across multiple processes.

Why it is especially close:

```text
UNSTRUCTURED BUYING PROBLEM
→ STANDARDIZED SPECIFICATION
→ INSTANT ECONOMIC BOUNDARY
→ CAPABILITY MATCH
→ EXTERNAL PROVIDER
→ QUALITY / TIMELINESS GOVERNANCE
→ REPEAT ORDER
```

Lesson for this project:
- convert people/firms from biographies into callable capability units;
- own the interface, acceptance, routing logic and trust layer rather than the factory;
- unused capacity becomes economically useful only after specification + price + trust + acceptance are solved.

Sources:
- https://www.xometry.com/how-xometry-works/
- https://www.xometry.com/resources/blog/answers-to-most-frequently-asked-questions/
- https://www.xometry.com/capabilities/community/

### C. Full Truck Alliance / 满帮 — idle-capacity flow + transaction rails

Observed mechanism:
- connects shippers and truckers;
- evolved from freight listings to end-to-end transaction infrastructure;
- offers matching and brokerage rather than merely exposing phone numbers;
- by Q2 2026 reported millions of monthly shippers/truckers and 68.5 million fulfilled orders in the quarter.

Why it matters:

```text
IDLE / SEARCHING CAPACITY
+
FRAGMENTED DEMAND
+
HIGH SEARCH / TRUST / COORDINATION FRICTION
→ MATCHING
→ TRANSACTION
→ SERVICE QUALITY / VALUE-ADDED LAYER
```

Lesson:
- a directory is weak;
- monetizable orchestration appears when the platform reduces search, trust, matching and transaction friction;
- settlement/contract rails can be as important as discovery.

Sources:
- https://ir.fulltruckalliance.com/Company-Profile
- https://ir.fulltruckalliance.com/Investor-FAQ

### D. GLG — humans as callable sensors / knowledge nodes

Observed mechanism:
- connects clients to professionals with first-hand experience;
- routes client questions into calls, meetings, surveys, workshops and other expert interactions.

Why it matters:

```text
CLIENT QUESTION
→ IDENTIFY WHO HAS FIRST-HAND REALITY
→ OPTION EXPERT TIME
→ CONTROL INTERACTION FORMAT
→ DELIVER EVIDENCE / INSIGHT
```

Lesson:
- human beings can be part of the sensor layer without becoming employees;
- the operator does not need to personally know every industry;
- the asset is discovering, qualifying and making expert access callable.

Difference:
- GLG primarily sells insight, not full downstream execution.

Source:
- https://www.glginsights.com/overview/

### E. Catalant / Business Talent Group — high-skill work made contractible

Observed mechanism:
- enterprise clients bring a project/need;
- platform/service layer helps scope the work and curate independent consultants/experts;
- contracting, compliance and payment are standardized;
- independent experts perform the work rather than the platform founder.

Why it matters:

```text
VAGUE ENTERPRISE NEED
→ PROJECT SCOPE
→ CURATED CAPABILITY MATCH
→ CONTRACT / COMPLIANCE
→ DELIVERY
→ CLIENT APPROVAL
→ PAYMENT / REPUTATION
```

Lesson:
- sophisticated knowledge work can be decomposed and routed;
- enterprise access and payment complexity themselves are valuable friction-removal layers;
- provider independence is compatible with a strong orchestrator.

Sources:
- https://catalant.com/for-independent-consultants/
- https://catalant.com/marketplace-partnerships/
- https://businesstalentgroup.com/
- https://businesstalentgroup.com/why-btg/

### F. Braintrust / Toptal — useful but also a warning boundary

Observed mechanism:
- enterprise demand is matched to vetted independent talent;
- platforms provide screening, matching and enterprise administration.

Useful lesson:
- verification and matching can materially reduce hiring/search friction.

Warning:
- if the unit remains merely `PERSON + HOURS`, the model can collapse toward staffing/body-shopping.
- this project should prefer `OUTCOME / CAPABILITY UNIT + ACCEPTANCE` where possible.

Sources:
- https://www.usebraintrust.com/products/talent-marketplace
- https://www.usebraintrust.com/pricing
- https://www.toptal.com/how

The closest external analogue is not one company. It is:

```text
GLG
  human sensors / first-hand reality
+
CATALANT / BTG
  expert capability packaging + enterprise contracting
+
XOMETRY
  machine-readable specification + routing + QA
+
LI & FUNG
  multi-node orchestration across an end-to-end outcome
+
FULL TRUCK ALLIANCE
  search/trust/transaction rails for fragmented capacity
```

The project's intended extension is broader:

```text
WORLD SENSING
→ FLOW-POTENTIAL DETECTION
→ ACTOR / RESOURCE / CAPABILITY DISCOVERY
→ ACCESS / SCOUT ROUTING
→ TASK / OUTCOME STRUCTURING
→ PROVIDER ROUTING
→ ACCEPTANCE / SETTLEMENT
→ REPEAT / LEARNING
```

This means the engine should be capable of routing not only execution resources, but also the **people and channels that discover reality**.

## 7. Implication for the current technology-manager route

Technology manager is now classified as one possible:

```text
ACCESS_PROVIDER
+
FIELD_SCOUT
+
DOMAIN_TRANSLATOR
```

It is **not** the founder's required occupational identity.

The current route must therefore test two paths in parallel conceptually:

```text
PATH 1 — FOUNDER ACCESS ASSET
Founder obtains a legitimate identity/participation path only if it cheaply improves credibility, rule understanding or institutional access.

PATH 2 — ROUTABLE ACCESS / FIELD-SCOUT CAPABILITY
Find an existing technology manager / institutional practitioner / domain scout who already has the relevant access and can be optioned under explicit incentive + evidence rules.
```

If Path 2 is cheaper, faster and produces better evidence, it should outrank founder self-performance.

## 8. Route-selection upgrade

For every candidate route, add these execution questions:

```text
WHO SENSES THE REALITY?
WHO HAS LEGITIMATE ACCESS?
WHO PERFORMS THE WORK?
WHO VALIDATES THE WORK?
WHICH OF THESE MUST BE THE FOUNDER?
WHY?
CAN THAT ROLE BE OPTIONED INSTEAD?
WHAT DOES THAT ACTOR GET?
WHAT EVIDENCE / ACCEPTANCE MAKES THE ROLE GOVERNABLE?
```

A route whose economics disappear when the founder stops doing operational labor is not yet an orchestration route.

## 9. P0 correction

The next field objective is no longer narrowly:

```text
FOUNDER BECOMES TECHNOLOGY MANAGER
→ FOUNDER ENTERS ENTERPRISE
→ FOUNDER DISCOVERS NEED
```

It is:

```text
IDENTIFY A LEGITIMATE SENSOR / ACCESS ROLE
→ OPTION THE ROLE OR THE ACCESS PATH
→ GIVE IT A COUNTERPART-VISIBLE INCENTIVE
→ DEFINE THE EVIDENCE CONTRACT
→ RECEIVE REAL FIELD TRUTH
→ ORCHESTRATOR JUDGES / ROUTES
```

Founder participation remains allowed when needed for calibration, but should be explicitly minimized and measured.
