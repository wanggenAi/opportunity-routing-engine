# Operator Identity Packet — Field Access v1

Date: 2026-09-15
Status: `P0 / TRUTHFUL / MINIMUM DISCLOSURE`

Purpose: answer the first question every serious external actor has before spending scarce time:

> **Who is this person, and why is this person relevant enough to admit into the conversation?**

This packet is not a résumé, sales brochure or invented institutional identity. It is the minimum truthful identity layer for the current field route.

## Public-facing identity

Recommended short form:

> 计算机工程背景，长期做企业软件与系统交付相关工作，熟悉 Java、数据库、系统边界和交付流程。目前在徐州做企业数字化项目中“高价值人员时间被重复性工作占用”这一类问题的实地验证，目标是把真实任务拆成可脱敏、可验收、可按结果协作的能力单元，而不是推软件、卖人头或承包整个系统。

Recommended institutional form:

> 我是计算机工程背景，过去多年从事企业软件、Java、数据库和系统交付相关工作。现在希望在徐州技术转移/数字化服务生态里做真实需求挖掘和任务结构化实践：把企业模糊的问题转成可验证的任务、能力和验收边界，再判断是否存在合规的资源匹配或技术合作路径。我希望在已有机构规则下参与真实项目，而不是借机构名义做销售。

## Evidence that may support the identity

Use only evidence the operator is willing and able to prove:

```text
EDUCATION
- computer-engineering bachelor's degree / graduation evidence

PROFESSIONAL
- multi-year enterprise-software work history
- Java / database / systems / delivery experience
- accepted project / employment evidence where disclosure is lawful and useful

TECHNICAL
- public code / GitHub work where relevant
- bounded sample showing task decomposition / acceptance design

LOCAL EXECUTION
- Xuzhou-based field availability when applicable
- ability to meet locally and perform structured discovery
```

Do not publish personal identifiers, old contracts, customer data, confidential project material, private employer records or unnecessary document scans in this public repository.

## What this identity proves

It may make the following claims plausible:
- the operator can understand technical delivery conversations;
- the operator can ask structured questions about systems, data, workflow and acceptance;
- the operator can translate vague work into bounded task interfaces;
- the operator has enough technical literacy to avoid treating enterprise delivery as generic gig work.

It does **not** prove:
- authority to represent any institution;
- permission to access enterprise data;
- technology-manager affiliation;
- supplier status;
- customer trust;
- transaction rights;
- any specific commercial result.

## Identity rule

```text
REAL BACKGROUND
→ LEGIBLE RELEVANCE
→ REQUEST PERMISSION
```

Never:

```text
REAL BACKGROUND
→ IMPLIED AUTHORITY
```

The operator's education and experience are **access capital inputs**, not entitlement to attention.

## 30-second spoken version

> 我是计算机工程背景，之前一直做企业软件、Java、数据库和系统交付。现在人在徐州，想做一件很具体的事情：不是卖软件，也不是介绍程序员，而是把企业交付里那些模糊、重复、占高级人员时间的工作，先拆成明确输入、输出和验收，看哪些真的能通过更好的资源组织解决。我现在只做真实项目验证，不能验证的我就不做。

## When an institution asks “what can you contribute?”

> 我能贡献的不是一个现成客户名单，而是技术理解、系统分析和结构化需求能力。我可以在规则允许的范围内做企业需求访谈、问题拆解、技术需求清单、可执行任务边界和证据记录，并把哪些事情可做、不可做、为什么不可做明确留下来。如果机构有真实项目或带教机制，我更希望先在真实案例里证明能力。

## Minimum disclosure principle

The identity packet should become stronger through accepted outcomes, not longer biographies.

Preferred progression:

```text
EDUCATION / EXPERIENCE
→ SUPERVISED REAL CASE
→ ACCEPTED OUTPUT
→ REFERENCE / BACKING
→ REPEATABLE ACCESS CAPITAL
```

The first real accepted case is more valuable than adding more self-description.
