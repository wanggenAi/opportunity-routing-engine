# Discovery Cycle 002 — Xuzhou Money-Capture Mechanics

Status: `DOWNGRADED / EXPLICIT_DEMAND_EXECUTION / NOT CORE DISCOVERY`

Date: 2026-09-12

Constitutional parent: `docs/LATENT_VALUE_DOCTRINE.md`

## 1. Why this document was downgraded

The earlier version promoted a plausible route in which digital-transformation service providers with existing projects could outsource bounded implementation, integration, remediation or operations tasks to an orchestrated execution backend.

That route may still be commercially valid.

However, it begins from **already-recognized project demand** and therefore belongs to:

```text
candidate_class = EXPLICIT_DEMAND_EXECUTION
```

It must not define the repository's core discovery direction.

The core engine now distinguishes:

```text
LATENT_VALUE_ACTIVATION
= discover value not yet recognized/packaged/combined as a market object

EXPLICIT_DEMAND_EXECUTION
= execute, match or coordinate an already-understood need
```

`EXPLICIT_DEMAND_EXECUTION != CORE_LATENT_VALUE_DISCOVERY`.

## 2. What remains valid

The following commercial truth from the previous analysis remains useful if this route is tested as a **cash-flow experiment**:

```text
IDENTIFIED PAYER
+
BOUNDED ACCEPTED OUTPUT
+
REAL PAYMENT PATH
+
DELEGATABLE EXECUTION
+
POSITIVE NORMALIZED ORCHESTRATION MARGIN
→ COMMERCIAL ROUTE HYPOTHESIS
```

A provider-paid CapabilityUnit could still be tested if:
- the provider has real bounded overflow;
- external execution is contractually/legal allowed;
- acceptance is explicit;
- actual settlement occurs;
- the operator is not the permanent executor;
- coordination/QA/replacement creates durable value.

But success here would prove only that one explicit-demand execution route can make money. It would **not** prove that this is the engine's core latent-value business.

## 3. What is no longer allowed

The repository must not infer:

```text
visible project activity
→ therefore this is our main opportunity
```

or:

```text
clear payer
→ therefore highest research priority
```

or:

```text
strong operator skill fit
→ therefore latent value exists
```

The core discovery sequence must instead remain:

```text
MACRO
→ MONEY FLOW
→ PSYCHOLOGY
→ BEHAVIOR
→ INDUSTRY STRUCTURE
→ ACTOR STATE / ENDOWMENT
→ HIDDEN / UNDERRECOGNIZED VALUE
→ COMPLEMENTARY ACTOR
→ TRANSFORMATION MECHANISM
→ EVIDENCE / VALIDATION
→ ONLY THEN TRANSACTION DESIGN
```

## 4. Relationship to Issue #54

Issue #54, `Paid Unit 001: prove provider-paid execution overflow`, remains a **downstream optional commercial validation**.

It is useful for testing whether the project can generate cash through an explicit-demand route.

It must not:
- determine the Cycle 002 core winner;
- suppress hidden-value exploration;
- receive first-found privilege;
- turn the project into a software-outsourcing backend by default.

## 5. Governing conclusion

> **A route can be profitable and still be architecturally secondary.**

The repository's primary job is not to wait for visible work and route executors faster. Its primary job is to discover value that actors themselves have not yet recognized, then create the transformation and exchange structure that makes that value real.

The digital-transformation execution backend is therefore retained as a possible `EXPLICIT_DEMAND_EXECUTION` experiment and removed from the core latent-value ranking.
