## F1 — Existing merchant API -> transactional Agent Skill compiler

Alipay's current merchant guide leaves search, selection, confirmation and order creation to the merchant's own order Skill, then hands payment to the Alipay payment Skill. WeChat AI Pay similarly requires a merchant Skill, preserves the traditional order flow, adds x402 and uses SkillHub for distribution.

This looks like a temporary integration gap, but public merchant-Skill generators already automate the informational Skill/MCP layer. OpenLuckin is stronger evidence: it wraps an official merchant MCP into real store/product search, order preview, real order creation, payment-link handling and order-status retrieval.

The remaining hard work is merchant-specific semantics, auth and lifecycle integration. Payment and distribution remain platform-owned. Without a proprietary standardized adapter/outcome graph, this collapses toward generic code generation or bespoke integration.

**Verdict:** demote.

## F2 — Housekeeping credit -> service match/order router

MOFCOM is embedding 家政信用查 into the operating flow: consumer order -> enterprise dispatch -> worker acceptance/query authorization -> result pushed to the consumer. It describes 家政信用查 as a mother platform combining authoritative data, local-government data and enterprise evaluation. Large firms get interface integration; SMEs are supported through standardized third-party platforms.

New national standards also cover e-commerce housekeeping service flow, worker onboarding audit and platform quality evaluation.

Trust becomes more usable, but the obvious trust-routing edge is internalized. Actual service quality, scheduling and exceptions remain physical human delivery.

**Verdict:** demote.

## F3 — Merchant-authorized e-commerce after-sales action router

GB/Z 200-2026 is current. Platform APIs already expose structured after-sales state and merchant-authorized actions. Douyin's current surface includes order/refund queries and merchant review/refund flows under explicit capability and merchant authorization.

Routine state-to-action cases are callable, but the action right belongs to merchant/platform credentials. A general Agent or ERP with the same authorization can execute the same routine calls. Hard cases retain evidence, policy, communication and negotiation work.

No distinct cross-platform realized-decision asset or operator action right was evidenced.

**Verdict:** demote.

## F4 — Natural-language cloud operations guardrail/router

Alibaba Cloud OpenAPI MCP Server Core makes the cloud control plane broadly callable from common agents through natural language. It supports OAuth/static credentials, RAM permissions, multi-account roles, multi-step orchestration and Terraform resource management.

This lowers callability friction; it does not transfer control. Resource identity, permission and audit remain in the provider/account control plane. External approval/policy layers are generic workflow functions unless they own a non-commodity policy or realized-outcome asset.

**Verdict:** demote.

The Scan 128 lesson is that **newly callable actions do not automatically create operator control**. AI payment, after-sales APIs and cloud MCP reduce execution friction, but here the decisive permission/distribution/control surfaces remain with platforms or participant accounts.

Scan 129 should move away from provider-owned payment/action rails and search for **small-operator-acquirable, transferable micro-assets** with native inbound, native payment and objectively machine-auditable delivery with low recurring labor.
