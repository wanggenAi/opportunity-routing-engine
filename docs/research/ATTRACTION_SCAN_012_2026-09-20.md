## Direction 1 — sudden shift vacancy → external flexible labor

This is almost the ideal topology:
- an employee calls out or is temporarily transferred;
- the private WFM sees an empty shift;
- the value of a qualified external worker jumps immediately;
- the decision window is short.

But current WFM/zero-gig products already own the complete event-to-failover loop.

GaiaWorks documents:
- leave / temporary transfer creates an empty shift;
- WFM automatically converts it into a task with city/hourly wage;
- the task is synchronized to the MILI flexible-work platform;
- qualified part-time workers are automatically targeted;
- the flow requires no manual intervention;
- completed work can flow into immediate settlement.

Source:
https://www.gaiaworks.cn/post/gaiaworks-news-202509099.html

Verdict:
`EXCEPTION_SIGNAL_PLUS_EXTERNAL_LABOR_FAILOVER_ALREADY_INTEGRATED`.

This is mechanism validation, not an opportunity.

Sources:

Warehouse execution APIs are mature:
- inbound order;
- outbound order;
- inventory;

- warehouse-provider connectivity.

Representative source:
https://developer.alibaba.com/docs/api.htm?apiId=26760

### Decisive action-gap

The public capacity platform still presents the commercial flow as:
- find warehouse;
- post demand;
- match / connect;
- contact / cooperate.

Current evidence does not establish a general rail for:
- real-time capacity lock;
- live standardized price;
- immediate acceptance;
- machine booking of a new warehouse relationship.

Warehouse APIs are strong **after a warehouse relationship has been selected**. They
do not prove that an overflow exception can automatically buy a previously unrelated
warehouse slot.

Verdict:
`RESOURCE_VISIBILITY_STRONG / EXECUTION_API_STRONG / NEW_CAPACITY_ACQUISITION_STILL_NOT_CALLABLE`.

This is a near-miss, not a retained formation.

## Cross-direction structural law — the failover integration trap

Scan 012 establishes:

```text
STANDARDIZED + CALLABLE + REPEATED
→ INCUMBENT INTEGRATION PRESSURE

UNOWNED + PHYSICAL + HETEROGENEOUS
→ HUMAN CONFIRMATION PRESSURE
```

This explains why the target repeatedly disappears at the hard floor.

Examples:
- labor: callable → WFM already auto-fills vacancy;
- logistics: callable → TMS/visibility platform already re-tenders/reroutes;
- payments: callable → orchestration layer already auto-switches;
- charging: callable → automaker/charging ecosystems already integrate low-battery response;
- warehouse overflow: capacity visible, but new capacity acquisition is still not
  machine-callable;
- emergency physical services: urgent, but field conditions keep the action manual.

## Important new infrastructure shift

A new rail is emerging in 2026 that can change the second half of this dichotomy.

Alipay Agent Pay now explicitly connects Agents to:
- physical goods;
- local/life services;
- digital resources.

It supports the Agent-side sequence:
- understand user need;
- search/select/confirm inside the merchant Skill;
- create order;
- hand payment to the payment Skill;
- receive result and continue fulfillment.

Sources:
- https://aipay.alipay.com/products/agent-pay
- https://aipay.alipay.com/merchant-guide
- https://aipay.alipay.com/docs/overview.html

Existing merchants can wrap an already-existing service flow as a Skill. Therefore a
service that was previously browser/app/manual-orderable may cross into
**machine-callable commerce** without the event-side system owning it yet.

This is a mechanism change, not a commercial candidate.

`NEWLY CALLABLE PHYSICAL/SERVICE RAIL × UNOWNED HIGH-INTENT SIGNAL`

Search broad current reality for rails where:
1. a physical/service resource was historically app/browser/manual/order-by-contact;
2. in 2026 it has newly become API-, MCP-, Skill- or Agent-callable;
3. the new rail exposes enough selection, price/quote, order/booking and result state to
   execute without case-by-case founder labor;
4. a separate high-intent state/event exists outside the rail owner's system;

- "Agent-callable" only means payment, while selection/acceptance is still manual;
- merchant-by-merchant onboarding becomes the operator's recurring job;
- the event side already offers the same substitute natively;
- the service requires recurring expert diagnosis or negotiation;
- the paid function is generic search with no state-dependent value jump.
