## Why most outcome-routing directions were killed quickly

Current payment orchestration, SMS routing, same-city delivery and AI/API gateways
already use live success/failure/cost/latency outcomes to improve routing. That proves
the mechanism is commercially real, but also shows that obvious transaction-generated
routing loops are rapidly internalized by incumbents.

Therefore Scan 015 did not retain:
- payment-success routing;
- SMS multi-channel routing;
- local-delivery carrier routing;
- generic model/API provider routing.

The residual search moved to a consumer transaction where:
1. the public quote is not the economically decisive outcome;
2. the final outcome is revealed only after fulfillment/inspection;
3. multiple independent rails exist;
4. the rails expose partner-callable transaction flows;
5. at least two rails expose partner economics;
6. cross-rail outcome history is not naturally owned by any single rail.

## F1 — Used-device realized-payout router

### The real decision is not the displayed estimate

For a user selling a used phone/tablet/computer, the economically relevant object is:

```text
DISPLAYED ESTIMATE
!=
FINAL REALIZED PAYOUT
```

A current Aihuishou service page explicitly says the online estimate is a reference
price and the final transaction price depends on physical inspection and user
confirmation. If the inspected offer is lower, the user may reject it and request
return.

Primary sources:
- https://www.aihuishou.com/
- https://www.aihuishou.com/ahs-services/v3/

This means the route has a real hidden outcome:
- inspection adjustment;
- accept / reject;
- final payout;
- elapsed time / return path.

- H5;

Its public cooperation FAQ explicitly describes a commission model:
