## 1. Why this sub-candidate exists

The parent candidate `LV-XZ-003` established that a university technology asset may become more valuable when patents, inventor know-how, validation capability and an industrial outcome are composed into one bounded capability bundle.

This document tests one concrete version of that idea:

> Can separately visible CUMT capabilities in sensing, fault diagnosis, digital twins, edge AI and concept validation be combined — with explicit authorization — into a **small, outcome-defined condition-monitoring / predictive-maintenance pilot** for a Xuzhou equipment actor that cannot justify a large platform project?

This is **not** a claim that CUMT currently sells such a bundle.

It is also not a claim that a faculty research direction is transferable IP.

Locked boundary:

```text
RESEARCH CAPABILITY
!= TRANSFERABLE IP
!= AUTHORIZED BUNDLE
!= ENTERPRISE-WORTHWHILE PILOT
!= PAID TRANSACTION
```

## 2. Origin-side evidence

Public CUMT evidence shows multiple relevant but separate capability elements:

- industrial machine vision, multi-source temperature/vibration/sonar sensing, fault diagnosis and predictive maintenance;
- edge/cloud AI deployment architecture;
- rotating-equipment and bearing fault diagnosis;
- digital-twin-driven heavy-gear fault prediction;
- intelligent diagnosis and O&M for complex electromechanical equipment;
- equipment lifecycle / health-management systems;
- concept-validation infrastructure covering technical, prototype, scenario and commercial validation.

These observations establish a **capability neighborhood**. They do not establish one commercial bundle.

## 3. Complementary-side evidence

The most useful current Xuzhou signal is not a generic digital-transformation slogan.

During a 2026 expert-enterprise visit, a Xuzhou engineering-machinery enterprise publicly described three concrete problems, including:

- severe operating conditions causing core-component fatigue and short life;
- insufficient digitalization;
- high implementation cost for fault prediction and online monitoring.

That is a materially stronger complementary-state signal than a procurement notice because it describes the operational state that could make a cheaper condition-monitoring route valuable.

The project still must determine whether this state exists in **smaller / mid-sized actors** where a narrow bundle creates incremental economics rather than competing directly with a large OEM's internal platform.

## 5. Why it may be genuinely latent

The individual components are not hidden. Many are publicly described.

The potentially latent value is the **cross-boundary composition**:

- faculty teams are organized around research programs;
- IP/software/technical services may have separate ownership and approval routes;
- enterprise actors think in machine downtime, false alarms, inspection labor and deployment cost;
- validation infrastructure exists but must still be connected to the exact industrial outcome;
- no public evidence currently shows one actor packaging these specific pieces into a low-cost bounded route.

Therefore the current missing evidence is deliberately:

`STRANDING_BARRIER`.

The engine must prove that this composition gap is real rather than merely imagined.

## 6. First machine-class hypothesis

Do **not** start with all engineering machinery.

The first validation should prefer a machine class with:

- measurable downtime or component-failure cost;
- accessible non-sensitive sensor signals;
- a narrow set of recurring failure modes;
- no safety-critical autonomous control requirement in the first pilot;
- enough repetitions to compare baseline and pilot;
- target actors who cannot justify a large full-stack monitoring platform.

Public CUMT work makes rotating equipment / bearings / gearboxes / compressors plausible search zones, but this document does not select a winner without enterprise-side baseline evidence.

## 7. Decisive validation — three stages

### Stage A — authorized asset inventory

Use only official/authorized CUMT technology-transfer or technology-manager channels.

For one machine class, answer:

1. Which exact patents, software, technical secrets, testing services or know-how are actually transferable/useable?
2. Who owns each asset?
3. Can they be combined in one transaction/pilot?
4. What approval, attribution, confidentiality and revenue-sharing constraints apply?
5. Is a faculty/team service component required, or can the output survive as a reusable module?

**Pass A** only if a real 3–5 element bundle can be legally/contractually assembled.

### Stage B — enterprise baseline

Interview 5–10 target Xuzhou actors in one machine class.

Do not ask `Do you want AI predictive maintenance?`

Capture:

- failure mode;
- annual/quarterly frequency;
- downtime or replacement cost;
- current inspection/maintenance method;
- sensors/data already available;
- false-alarm tolerance;
- installation/access constraints;
- maximum acceptable pilot cost;
- decision-maker and payer;
- what measurable result would justify continuation.

**Pass B** only if at least one repeated, expensive-enough problem exists with a bounded acceptance metric.

### Stage C — commitment

Define one minimal pilot such as:

```text
one machine class
+ one/two failure modes
+ minimum sensor set
+ fixed deployment boundary
+ diagnosis / warning output
+ measurable false-positive / detection / lead-time / cost criterion
+ fixed pilot period and price
```

**Pass C** requires both:
- university-side authorization for the actual capability stack;
- enterprise-side concrete commitment: paid pilot, signed pilot/LOI with decision condition, or equivalent costly commitment.

Generic interest is not a pass.

## 8. Kill conditions

Kill or sharply downgrade `LV-XZ-003A` if:

- transferable assets cannot be combined;
- the relevant university capability already exists as an efficient ready-made product/channel and we add no structure;
- target actors can buy an adequate commodity monitoring product more cheaply;
- sensor installation/data collection dominates cost;
- failure events are too rare to validate;
- data/industrial-security constraints block the route;
- firms will praise the idea but make no bounded commitment;
- the orchestrator is only forwarding contacts;
- economics require the operator to become a permanent engineer/salesperson.

## 9. Orchestrator's possible value — only if validated

The operator's value would be:

```text
industrial outcome translation
→ asset/capability composition
→ rights / interface clarification
→ pilot architecture
→ acceptance design
→ expert / enterprise coordination
→ evidence and settlement loop
```

Not:

```text
sell professor contact
sell patent list
sell AI buzzword
write software personally forever
```

Potential capture structures after proof may include an authorized technology-manager/transaction service fee, pilot-orchestration fee, or success-linked share. The exact legal/contractual structure remains `UNKNOWN` until authorized channels confirm it.
