# ATTRACTION_SCAN_003-F1 — Causal Descent / Acceptance-Rail Resolution

Date: 2026-09-19  
Epoch: `ATTRACTION_FIELD_V1`  
Formation: `ATTRACTION_SCAN_003-F1 — AI CUSTOM-SERVICE ACCEPTANCE RAIL`  
Verdict: `SURVIVES_CAUSAL_DESCENT / READY_FOR_CHEAP_REALITY_CONFIRMATION / NOT_A_COMMERCIAL_CANDIDATE`

## Executive truth

F1 is the first post-reset formation that survives causal descent.

It does **not** survive in its original broad form.

The broad statement:

> “AI custom services need clearer acceptance.”

is too generic and is already addressed by:
- providers' own SOW / milestone processes;
- free acceptance templates;
- outsourcing marketplace milestones and dispute rails;
- cloud Agent evaluation tools;
- formal third-party testing;
- project diagnosis / PoC acceptance consulting.

The formation survives only after narrowing to:

`AI WORKFLOW / AGENT DELIVERY ACCEPTANCE EVIDENCE`

for transactions where the AI system is expected to **perform observable business actions**, not merely generate subjective text.

The surviving state transition is:

```
BUSINESS WORKFLOW BRIEF
→ AGREED STATE-CHANGE / TOOL-CALL / FALLBACK CONDITIONS
→ FROZEN TEST FIXTURES
→ EXECUTABLE RUN
→ TRACE + OUTPUT + COST/LATENCY EVIDENCE
→ PASS / FAIL / RETEST
```

This is materially different from selling an acceptance checklist.

The remaining hypothesis is:

> A middle-value AI workflow/Agent transaction may support a lightweight independent acceptance artifact when generic marketplace mediation is too weak and formal third-party testing/consulting is too heavy.

That hypothesis has enough structural support to justify a **cheap external reality confirmation**, but not enough evidence to promote a commercial candidate.

## 1. Causal decomposition

### Surface symptom

AI custom-service buyers and providers disagree about whether the project is “done.”

### Root cause candidates

#### C1 — no contract / milestone rail exists

Result: `REJECTED`.

Existing outsourcing marketplaces already support staged delivery, acceptance and payment/dispute handling.

Examples:
- Zhubajie AI service pages explicitly expose staged acceptance/payment;
- Xianyu already provides order/payment and dispute infrastructure.

Therefore:

`PAYMENT RAIL != MISSING EDGE`.

#### C2 — nobody knows what AI acceptance should include

Result: `WEAKENED`.

Current public material already provides extensive free guidance:
- business outcome;
- task quality;
- tool execution;
- permissions;
- logs;
- failure/fallback;
- latency/cost;
- test sets;
- retest rules.

Examples:
- https://www.moredist.com/blog/ai-workflow-acceptance-metrics/
- https://aopc.ai/stacks/client-project-scope-change-acceptance/
- https://aizvl.com/insights/next-vendor-agent-acceptance-standard
- https://aswork.cn/news/aswork-staged-ai-delivery-verification/

Therefore:

`ACCEPTANCE KNOWLEDGE / CHECKLIST != MISSING EDGE`.

#### C3 — evaluation engines do not exist

Result: `REJECTED`.

Cloud AI platforms already provide evaluation datasets, rules, judges and benchmark workflows.

Formal third-party vendors already test AI/software systems.

Therefore:

`GENERIC EVAL TOOLING != MISSING EDGE`.

#### C4 — project diagnosis / PoC acceptance support does not exist

Result: `REJECTED AS GENERAL CLAIM`.

Current providers already sell or demonstrate:
- pre-PoC diagnosis;
- frozen test sets;
- acceptance metrics;
- contract/acceptance conditions;
- vendor/quote review.

Direct adjacent example:
- https://www.ciyuantask.com/report-demo

The direct incumbent is important because it validates the problem but also removes “AI acceptance consulting” as an open generic space.

#### C5 — an agreed acceptance definition is not converted into executable transaction evidence

Result: `SURVIVES FOR A NARROW CATEGORY`.

This is the strongest residual.

A free template may tell parties to define:
- task success;
- tool calls;
- permissions;
- cost;
- fallback;
- logs.

But the transaction still needs a reproducible object that can answer:

```
WHAT WAS AGREED?
WHAT EXACT INPUT WAS TESTED?
WHAT VERSION / ENVIRONMENT RAN?
WHAT ACTIONS OCCURRED?
WHAT STATE CHANGED?
WHAT FAILED?
WHAT EVIDENCE EXISTS?
CAN IT BE RETESTED?
```

For action-oriented AI workflows, much of this evidence is technically observable.

Truth state: `STRUCTURALLY DISTINCT / MARKET DEMAND FOR SEPARATE LAYER NOT YET PROVEN`.

## 2. Ticket-size causal test

The first scan identified a possible low-ticket/high-ticket barbell. Current listings strengthen that view.

### Low-ticket

Current AI service listings can be as low as tens or hundreds of RMB, and generic templates can list around hundreds of RMB.

Examples:
- Zhubajie AI service listings include low-cost template/basic tiers.

At this level:
- independent acceptance overhead is likely disproportionate;
- platform mediation and simple checklists are likely sufficient.

Result: `ECONOMICALLY WEAK`.

### Middle-value band

Current listed / advertised AI workflow and Agent service packages include:
- approximately 10,000 RMB one-time standard Agent/workflow services on a cloud marketplace;
- 10,000 RMB standard and 40,000 RMB advanced Agent service tiers on a service marketplace;
- other current service providers publicly quote pilot/custom work in the several-thousand-to-tens-of-thousands range.

These are vendor/listing prices, not a population-wide market distribution.

Result: `MIDDLE BAND EXISTS AS OBSERVED OFFERING RANGE`.

### Formal third-party test band

Current testing-service references place small functional acceptance testing in the thousands of RMB and broader formal acceptance materially higher, with qualified/CMA/CNAS work often much more expensive.

Those are provider/industry reference prices, not an official universal tariff.

Implication:

A 10k–40k RMB AI workflow transaction may be:
- too valuable for purely subjective “满意不满意” acceptance;
- too small to comfortably carry a traditional independent test engagement.

Result:

`BARBELL DOES NOT KILL F1 YET`.

It instead narrows the decisive target to a middle transaction band.

## 3. Category decomposition

F1 fails if it tries to cover every AI service.

### Category A — open-ended generation / creative assistants

Examples:
- content generation;
- subjective conversational tone;
- open-ended creative work.

Problem:
- quality is highly preference-dependent;
- golden answers are expensive to define;
- human judgment remains dominant.

Result: `REJECT FOR CURRENT FORMATION`.

### Category B — generic software / AI-coded websites

Most functional acceptance can already use ordinary software testing.

Result: `NOT DISTINCTLY AI`.

### Category C — RAG / knowledge assistant

Observable:
- citation presence;
- retrieval source;
- refusal behavior;
- latency;
- access control.

But:
- golden-answer construction often requires business experts;
- semantic correctness may remain human-judged.

Result: `POSSIBLE BUT HUMAN-LABEL HEAVY`.

### Category D — AI workflow / Agent automation with tool use

Observable:
- trigger/input;
- required tool/API call;
- parameter constraints;
- workflow state transition;
- external system write;
- permission boundary;
- human approval gate;
- fallback behavior;
- logs/traces;
- latency;
- token/API cost;
- retry behavior.

Many acceptance facts are machine-observable.

Result:

`BEST SURVIVING WEDGE FOR CAUSAL TEST`.

This does not prove a business. It identifies the category with the strongest automation ratio.

## 4. Why “free template” does not automatically kill the wedge

Current public pages already give useful acceptance templates.

That commoditizes **knowledge**.

It does not necessarily commoditize:
- freezing a project-specific test fixture;
- executing the fixture against the delivered system;
- collecting trace evidence;
- versioning the result;
- reproducing a failed case;
- comparing retest runs.

The wedge therefore cannot charge for “knowing the checklist.”

It can survive only if the valuable object is:

`EXECUTED, REPRODUCIBLE TRANSACTION EVIDENCE`.

## 5. Automation test

The automation requirement is stringent.

A current engineering case reports AI assistance generating a large majority of test cases from requirements/code, with humans supplementing edge cases. This is directional evidence that test construction can be partially automated, not proof of the proposed service economics.

Source:
- https://developer.volcengine.com/articles/7555088484290002990

For the formation to survive:
- initial project brief must be structured quickly;
- most test skeletons must be generated automatically;
- provider supplies a runnable target / logs / sandbox;
- objective checks must dominate;
- human review must be exception-level, not every case.

Current result:

`TECHNICAL AUTOMATION = PLAUSIBLE / NOT MARKET-VALIDATED`.

## 6. Adjacent paid-service test

The existence of current paid project-diagnosis / PoC-acceptance support is a positive and negative signal.

Positive:
- buyers already pay for help around requirements, vendor evaluation and acceptance in at least some project states.

Negative:
- current services are report/consulting heavy;
- they may already capture the higher-value buyer;
- the proposed layer must not reproduce consultant labor at a lower price.

Direct adjacent example:
- https://www.ciyuantask.com/report-demo

Result:

`WILLINGNESS TO PAY FOR THE PROBLEM FAMILY = PARTIALLY EVIDENCED`

but:

`WILLINGNESS TO PAY FOR A LIGHTWEIGHT TRANSACTION RAIL = NOT PROVEN`.

## 8. Attraction Field after causal descent

### A-side attraction

Provider incentive remains strong:
- bounded scope;
- fewer subjective revisions;
- clearer tail-payment condition;
- reusable delivery evidence.

Result: `HIGH AS INCENTIVE / EXTERNAL ADOPTION UNPROVEN`.

### B-side attraction

Buyer incentive remains strong:
- less demo theater;
- evidence of actual workflow completion;
- clearer failure/retest path.

Result: `HIGH AS INCENTIVE / EXTERNAL ADOPTION UNPROVEN`.

### Operator attraction

Remains high **only** in the narrow automated evidence form.

The operator should own:
- schema/protocol;
- test primitives;
- evidence format;
- repeatability;
- template learning.

The operator should not own:
- bespoke requirements consulting;
- every test-set labeling task;
- manual QA;
- dispute adjudication;
- domain certification.

Result: `HIGH CONDITIONAL`.

### Weakest link

Actual bilateral willingness to adopt/pay for an independent acceptance object before work starts.

Result: `UNPROVEN`.

## 9. Operator non-labor test

The current narrowed wedge has a plausible non-labor path because workflow/Agent systems expose machine-observable events.

But it fails immediately if:
- every buyer needs long discovery interviews;
- every test case is handcrafted;
- the operator decides subjective quality;
- the operator manually reviews every run;
- the operator becomes final dispute judge.

Result:

`CONDITIONAL PASS FOR CHEAP VALIDATION / NOT PASS FOR COMMERCIAL PROMOTION`.

## 10. Self-propulsion / compounding test

Potential reusable assets:
- category acceptance schemas;
- common workflow assertions;
- tool-call rules;
- permission/fallback tests;
- failure-mode library;
- environment/version capture;
- evidence-pack format;
- retest history.

These can reduce future setup cost if projects share enough structure.

Result:

`PLAUSIBLE COMPOUNDING / NEEDS REAL TRANSACTION EVIDENCE`.

## 11. Permission / control-right density

The relevant rights are comparatively concentrated:
- buyer defines outcome and can accept;
- provider controls delivery;
- marketplace/payment provider controls funds/dispute state.

No local multi-stakeholder permission fabric like Scan 002 is required.

Result:

`ROUTABILITY ADVANTAGE SURVIVES`.

## 12. What is now proven versus unproven

### Proven enough for continued research

- current AI custom-service transaction volume is substantial;
- acceptance ambiguity is a current problem;
- a middle-value offering band exists;
- formal testing can be too heavy for some middle-value work;
- acceptance knowledge/templates are not the residual;
- workflow/Agent execution produces machine-observable evidence;
- current adjacent paid acceptance/PoC services validate part of the problem family.

### Still unproven

- a separate lightweight layer is wanted by both parties;
- either side will pay for it;
- sellers will freeze acceptance before work rather than after conflict;
- buyers will trust automated evidence;
- marketplace/payment rails will recognize/use the evidence;
- generation can be minutes rather than consulting hours;
- enough projects are structurally similar for compounding.

## 13. Verdict

F1 is **not demoted** and **not promoted**.

New state:

`SURVIVES_CAUSAL_DESCENT / READY_FOR_CHEAP_REALITY_CONFIRMATION`.

The formation is narrowed to:

> a lightweight, executable acceptance-evidence layer for middle-value AI workflow / tool-using Agent delivery.

This is the first post-reset formation allowed to consume a small amount of external validation capital.

## 14. Cheapest decisive reality confirmation

Do **not** build software.

The next validation must test the missing human/economic fact, not technical feasibility.

Required evidence target:

1. a current AI workflow/Agent buyer or provider with a real transaction-sized project;
2. a real project brief / service listing / SOW;
3. willingness from both sides to freeze 5–15 measurable acceptance conditions before delivery;
4. evidence that those conditions could determine closeout/retest;
5. evidence whether either side values this enough to adopt/pay or at minimum materially prefers the transaction with it;
6. evidence of setup effort required to create the pack.

Fail if:
- participants say normal milestone descriptions are enough;
- the project is too cheap to justify any extra layer;
- acceptance requires deep domain consulting;
- only one side wants it;
- the pack cannot be generated without substantial manual work.
