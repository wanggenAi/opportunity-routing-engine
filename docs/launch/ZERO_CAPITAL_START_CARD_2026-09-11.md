# ZERO-CAPITAL START CARD — First Demand Pump

Date: 2026-09-11
Status: `IMMEDIATE / ZERO-CAPITAL VALIDATION`

## Objective

Do **not** learn ERP/MES/supply-chain systems first. Do **not** sell a platform. Do **not** recruit a provider pool.

Resolve one question:

> Can one Xuzhou digital-service demand source expose a real, recurring, de-sensitive, bounded task that can be paid on accepted output?

The operator's job in this stage is to identify structure, not to become the system implementer.

## Zero-capital boundary

Before a real payer commitment:

- no office;
- no paid ads;
- no software/platform build;
- no broad freelancer/provider recruitment;
- no equipment purchase;
- no paid data acquisition;
- no advance purchase of software/licenses for a buyer;
- no promise to finance provider labor from operator capital;
- no task requiring production credentials, sensitive customer data or prohibited subcontracting.

Preferred first cash structure:

```text
buyer confirms bounded task + acceptance + price
→ buyer deposit / written payment commitment where feasible
→ only then source 2–3 providers for that exact CapabilityUnit
→ provider terms explicitly agreed
→ accepted result
→ settlement
```

Never promise a provider deferred payment unless they explicitly agree to those terms.

## What the operator needs to understand

When the counterpart mentions ERP, MES, WMS, CRM, supply chain, industrial internet or another large system, do **not** attempt to understand the whole system during first validation.

Ask only:

```text
1. What exact small task is consuming time?
2. What input/material is available?
3. What exact output must be produced?
4. What objective acceptance rule proves it is complete?
5. Can the task be de-sensitive and externalized lawfully/contractually?
6. How often does this task recur?
7. What does the current workaround cost in people-days or cash?
8. Would the owner pay for accepted output?
```

If these cannot be answered, the task is not yet routable.

## First task menu — deliberately simple

Prefer tasks that do **not** require deep ERP/MES domain ownership:

1. `DELIVERY_DOC_NORMALIZATION`
   - approved source → standardized delivery pack

2. `TRAINING_SOP_PACK`
   - approved product/process source → editable SOP / quick guide / training pack

3. `PUBLIC_RESEARCH_PACK`
   - public-source question → source-linked structured research result

4. `ANONYMIZED_SPREADSHEET_TRANSFORM`
   - de-identified sample/schema → cleaned/import-ready spreadsheet + validation report

5. `SANDBOX_TEST_EVIDENCE`
   - approved sandbox + test cases → evidence log / screenshots / defect list

6. `KNOWLEDGE_BASE_STRUCTURING`
   - approved non-sensitive docs → structured FAQ / knowledge base with provenance

7. `BOUNDED_NON-SENSITIVE_AUTOMATION`
   - narrow workflow + sample data → small script/tool + agreed test cases

## Explicitly reject first

- ERP/MES implementation ownership;
- production configuration changes;
- production database access;
- core system integration responsibility;
- official audit/acceptance conclusions;
- sensitive customer or production data without lawful authorization;
- hidden subcontracting contrary to upstream contracts;
- open-ended onsite support;
- safety-critical work;
- anything where success cannot be objectively accepted.

## Seven-minute probe

Ask in this order:

1. 过去30天，你们哪个已签项目最占实施人员时间？
2. 里面哪些事情重复、琐碎但必须完成？
3. 哪些必须由高级顾问判断，哪些只是按规则把结果做出来？
4. 最近一次这类任务是谁做的，花了多少人天？
5. 如果任务脱敏后，合同/客户允许外部协作吗？
6. 这个任务每个项目都会发生，还是偶尔发生？
7. 如果我把它写成明确输入、输出、验收和失败替换规则，你愿不愿意给一个真实的小任务按结果付费试一次？

## Evidence classes

```text
NO_TASK          = no real recent task
TASK_ONLY        = task exists but externalization/payment unknown
ROUTABLE_TASK    = bounded + de-sensitive + external collaboration allowed
PAID_COMMITMENT  = real price/payment commitment for accepted output
DEMAND_PUMP      = same source can name >=3 similar events or recurring task cadence
```

## First-day success

A successful first day does **not** require revenue.

Strong outcome:
- one real recent task is named;
- current workaround cost is understood;
- it is potentially routable;
- recurrence mechanism is known;
- exact person with payment/approval authority is identified.

Best outcome:
- one bounded task reaches `PAID_COMMITMENT`.

## What happens after one real task

Only then:

```text
real task
→ operator writes one CapabilityUnit card
→ acceptance test
→ price / buyer commitment
→ source 2–3 providers only for that card
→ small proof if needed
→ provider selected
→ execution
→ acceptance
→ settlement
→ ask the same Demand Pump for the next task
```

## Operator rule

The operator may attend the first conversations because these conversations are learning the transaction architecture.

The operator should **not** become the permanent salesperson or delivery worker.

As soon as the demand pattern stabilizes, outbound/relation access itself becomes a CapabilityUnit with an explicit payout rule.

## Governing question

> **Can I find one recurring stream of small accepted outcomes, then make other resources execute them while I keep the architecture, routing, incentives and governance?**
