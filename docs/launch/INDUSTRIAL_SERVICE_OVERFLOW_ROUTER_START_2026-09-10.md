# START HERE — Industrial Service Overflow Routing Network

Date: 2026-09-10
Status: `IMMEDIATE TARGETED VALIDATION`

Canonical project name:

> **制造业 / 数字化服务商交付溢出任务编排网络**

This is the current #1 structural candidate from `docs/research/RESET_OPPORTUNITY_SCAN_V1_2026-09-10.md`.

The goal is **not** to sell software to random factories and not to recruit a freelancer pool before demand exists.

The first goal is to prove one recurring `Demand Pump`:

> a service provider that already has enterprise customers and recurring project obligations releases one bounded, legally/contractually delegable overflow task and pays for accepted output.

## 1. The hook

Do not pitch `outsourcing people`.

Pitch:

> **交付溢出任务编排：只接可脱敏、可标准化、可验收、非核心权限的小任务。不是给你推人，而是把任务拆成明确输入/输出/验收，组织合适资源完成；按结果验收，执行资源失败可替换。**

Core contrast:

```text
NOT: 给你介绍一个程序员/学生
NOT: 我们什么软件都能做
NOT: 我来承包你的整个项目

YES: 给我一个真实的低杠杆/溢出任务
→ 我先定义任务边界
→ 你确认验收标准
→ 我组织执行资源
→ 结果达到标准才进入结算
```

## 2. First task menu — bait, not a rigid catalog

Use these only to make the conversation concrete. Ask for their real recent tasks first.

Safe initial candidates:

1. `DELIVERY_DOC_NORMALIZATION`
   - Input: approved non-sensitive source materials + required document list.
   - Output: standardized delivery-document pack.
   - Acceptance: required sections/fields complete, naming/version rules pass, source facts traceable.

2. `TRAINING_SOP_PACK`
   - Input: approved product/process source pack.
   - Output: user training deck / SOP / quick-start material.
   - Acceptance: defined topics covered, source-only claims, editable + export version.

3. `SANDBOX_TEST_EVIDENCE`
   - Input: demo/sandbox environment + approved test cases.
   - Output: execution record, screenshots/logs, issue list.
   - Acceptance: test-case coverage and evidence completeness.
   - Never request unauthorized production access.

4. `ANONYMIZED_DATA_TEMPLATE`
   - Input: de-identified sample / schema / transformation rules.
   - Output: normalized/import template + validation report.
   - Acceptance: schema/rule checks pass.

5. `PUBLIC_RESEARCH_PACK`
   - Input: research question and public-source boundary.
   - Output: source-linked competitor/customer/industry research pack.
   - Acceptance: coverage, provenance and required fields pass.

6. `KNOWLEDGE_BASE_STRUCTURING`
   - Input: approved non-sensitive documentation.
   - Output: structured FAQ/knowledge-base corpus with traceability.
   - Acceptance: schema, coverage, source links and duplicate checks pass.

7. `BOUNDED_INTERNAL_AUTOMATION`
   - Input: non-sensitive workflow/sample data.
   - Output: narrow script/tool with test cases.
   - Acceptance: agreed test cases pass.

## 3. Never accept first

- official third-party audit / evaluation / government acceptance decisions;
- accounting/legal/financial professional conclusions without qualified authority;
- hidden subcontracting where the upstream/customer contract forbids it;
- customer credentials or unauthorized system access;
- sensitive production/personal data without lawful handling and explicit authorization;
- uncontrolled production-line changes;
- safety-critical engineering;
- labor dispatch / disguised employment;
- open-ended `帮我们做实施` with no bounded deliverable.

1. 过去30天，哪个已签/在做项目最占实施团队时间？

## 9. First-cycle PASS / FAIL

Target exactly five qualified Demand Pump candidates.

PASS:
- >=3/5 name a real recent overflow task;
- >=2/5 identify a task that can be contractually/lawfully externalized and objectively accepted;
- >=1 makes a real paid pilot commitment.

Strong sustainability signal:
- the same organization says this task class appears monthly/per project/per deployment; or
- one organization can name >=3 similar task events from recent projects.

FAIL / redesign:
- no recurring overflow across qualified providers;
- useful work cannot be separated from core/sensitive/on-site responsibility;
- contracts prohibit external execution;
- direct freelancer/hiring dominates and QA/replacement adds no value;
- task economics cannot fund both provider payout and orchestration margin.

## 10. What happens only after a real task appears

Do **not** build the Capability Pool first.

Once one real task appears:

```text
1 real task
→ write CapabilityUnit specification
→ choose acceptance tests
→ establish buyer budget / payout condition
→ then source only 2–3 candidate providers
→ small proof task if needed
→ select provider
→ deliver
→ buyer accepts
→ settle buyer/provider/orchestrator
→ ask for next task from same Demand Pump
```

Potential supply channels only after demand:
- Xuzhou OPC communities;
- university/student technical capability where task is suitable and lawful;
- freelancers/specialists;
- local small studios;
- AI-assisted workflow under accountable human QA.

## 11. First economic rule

Do not optimize the first transaction for maximum take rate.

Prefer:

```text
payer price
- fair demand-source payout if applicable
- provider payout
- QA / replacement reserve
- operating cost
= cash contribution
- operator shadow labor
= normalized orchestration margin
```

The first transaction may have thin margin if it buys decisive information. The repeated template must eventually support positive normalized margin.

## 12. First sustainability milestone

Do not celebrate only the first payment.

The first serious milestone is:

> **One Demand Pump sends a second real task without restarting customer acquisition from zero.**

The stronger milestone is:

> **The same task template is completed by a different qualified provider and still passes acceptance.**

That is the beginning of the intended circulation system.

## 13. Stop building software

No marketplace UI, app, CRM clone or automated routing platform before:
- L4: one accepted paid transaction;
- L6: delegated repeat / provider replacement;
- L7: one Demand Pump repeatedly produces transactions and routing improves.

Until then, the product is the **transaction architecture and routing method**, not the website.
