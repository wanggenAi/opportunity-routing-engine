## Mission

The repository has reached the point where more internal completeness is no longer the default priority.

The next decisive proof must come from reality:

> **Cause one real external value flow by identifying an evidenced potential difference, reducing a real blocker, and reaching an accepted economic exchange.**

This mission exists specifically to prevent the project from becoming an indefinitely improving research/architecture system that never enters the world.

## P0 outcome

The first proof is:

```text
REAL EXTERNAL ACTOR
→ REAL RECENT PROBLEM / VALUED OUTCOME
→ IDENTIFIED PAYER WITH AUTHORITY
→ REAL CAPABILITY / RESOURCE
→ OBSERVED BLOCKER
→ BOUNDED ROUTE
→ ECONOMIC COMMITMENT
→ DELIVERY
→ OBJECTIVE ACCEPTANCE
→ SETTLEMENT
→ EVIDENCE PACKET
```

Money may be small. It must be real.

A symbolic transfer, friend/family favor, self-payment, invented invoice, non-binding expression of interest or simulated transaction does not pass.

## Launch clock

Target operating window after this mission reaches `main`:

- **within 24 hours** — select one executable route from the existing evidence/candidate pool; no new broad scan is required to make the selection;
- **within 72 hours** — obtain at least one new piece of direct external actor truth through a call, visit, message, application, meeting or other legitimate contact route;
- **within 14 calendar days** — aim for either `ECONOMIC_COMMITMENT` or a decisive falsification of the selected route;
- after falsification — immediately reuse the learned blocker/evidence to select the next existing route rather than reopening general architecture work.

These are execution targets, not fabricated success criteria. A truthful `REJECT` is preferable to an internally manufactured `PASS`.

## Architecture freeze

Until the first external value-flow proof or a decisive route falsification is captured, the following are **not P0 by default**:

- new ontology layers;
- new generic scoring dimensions;
- new broad-market taxonomies;
- new dashboards;
- new platform infrastructure;
- new generic agent frameworks;
- new sensors added only for completeness;
- more documentation that does not change an active field decision.

Work may interrupt the freeze only when it:

1. fixes CI / production reliability;
2. closes a specific truth gap blocking the active route;
3. enables a legitimate access or evidence path required by the active route;
4. automates a repeated manual bottleneck already observed in field execution;
5. corrects a material doctrine/truth violation.

The governing priority is:

```text
FIELD TRUTH > INTERNAL COMPLETENESS
```

when a cheap real-world test is already possible.

## Route-selection gate

Select a route from evidence already in the repository using these gates:

```text
R1  Is there a named/reachable Actor or legitimate access path?
R2  Is there a concrete valued outcome and plausible payer?
R3  Is there an evidenced capability/resource or a cheap way to option it?
R4  Is the blocker specific enough to test?
R5  Can the route be tested without large irreversible capital?
R6  Can success/failure be objectively observed?
R7  Does the orchestrator add more than a contact introduction?
```

A route with a lower theoretical upside but much stronger `R1-R6` may outrank a grander but inaccessible thesis for the **first proof**.

## First proof acceptance criteria

`FIRST_EXTERNAL_VALUE_FLOW = PASS` only when all are true:

- the need/outcome came from an external actor, not an invented scenario;
- the payer/authority was identified;
- the capability/resource used was real and voluntarily available;
- the blocker and the orchestrator's intervention were recorded;
- economics were explicit before or at commitment;
- output was delivered;
- an objective acceptance event occurred;
- settlement occurred;
- provenance/evidence is stored without exposing prohibited sensitive data;
- the system records whether the event is repeatable or merely one-off.

## What this mission is trying to learn

The first transaction is not primarily a revenue target.

It must answer:

1. Can the engine identify a real `FLOW_POTENTIAL` rather than merely describe social waste?
2. Can the operator gain legitimate access without pretending to own resources or authority?
3. Can a real task/outcome be decomposed into an accepted unit?
4. Can another actor provide capability under transparent terms?
5. What exact blocker does orchestration remove?
6. Is the payer willing to fund the incremental value?
7. Does the result make the next route easier, cheaper or more credible?

## Founder/operator constraint

The operator may personally perform part of the first proof when that is the cheapest honest way to learn the transaction boundary, especially where technical competence is relevant.

But founder labor must be recorded explicitly and may not be counted as zero cost.

The target system remains:

```text
OPERATOR LEARNS THE ROUTE
→ CAPABILITY IS MADE CONTRACTIBLE
→ PROVIDERS / CHANNELS BECOME REPLACEABLE OR COMPOSABLE
→ OPERATOR RETAINS DISCOVERY / ROUTING / GOVERNANCE ADVANTAGE
```

not permanent self-employment disguised as orchestration.

If `NO`, defer it.
